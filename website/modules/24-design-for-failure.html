🎯 Learning Objectives

By the end of today, you will be able to:

  1. Tell temporary failures from permanent ones, and handle each differently.
  2. Retry temporary failures with a limited number of attempts and growing waits.
  3. Make a retried run safe with an idempotency key.
  4. Keep the service useful in degraded mode when a dependency is down.

Plain idea: in production, failure is normal; decide in advance what each kind means so the service bends instead of breaking.

📚 Core Concepts

Observe: three bad nights

With real websites switched on (Day 22's flag), three things happen in the first month.

  1. A website answers slowly once, then fine. The Module 5 code treats a timeout as "no website" and sends the company to review, although one more try would have worked.
  2. The network is down for an hour. Every company goes to review as "no website", flooding the queue with cases that need no human judgement, and Day 21's alert fires.
  3. The batch crashes halfway and is restarted. Companies processed before the crash are processed again, and each now has two identical results in its history.

None of these is a bug in the classifier. They are the normal behaviour of networks and processes, and the service needs a designed answer for each.

Say it plainly: four designed answers

Temporary or permanent? A timeout is temporary: trying again may work. "This company has no website" is permanent: trying again will not help. Stage 06 gives them different exceptions. The HTTP adapter turns a TimeoutError into TemporaryWebsiteError, and keeps WebsiteUnavailable for permanent cases.

Retry temporary failures, a few times, with growing waits. RetryingWebsiteSource wraps any source. On a temporary error it waits 0.2 seconds, then 0.4, and gives up after three attempts. Growing waits give a struggling server room to recover instead of hammering it. Permanent errors are never retried. A timeout on each attempt (Day 10) puts a ceiling on how long one company can take.

Degrade, don't stop. When every retry fails, the source raises SourceDown. The core turns that into a result that needs review with a new reason, source_down, so the run finishes, nothing is lost, and the reason tells reviewers that these cases can simply be retried later rather than judged.

Make a repeated run harmless. Each batch run has a run ID. The store records each result with an idempotency key made from the run ID and the company ID, and migration 5 adds a unique index on it. If a crashed run is restarted with the same run ID, saving the same company again does nothing.

Name it: transient faults, backoff, idempotency, degraded mode

A transient failure is one that may succeed if tried again; a permanent failure will not. Exponential backoff doubles the wait between attempts. An operation is idempotent if doing it several times has the same effect as doing it once; the HTTP standard, RFC 9110, defines idempotent request methods in exactly this sense. SQLite's ON CONFLICT ... DO NOTHING clause (its "upsert" syntax) is what makes the second save a no-op. Degraded mode is running with reduced capability instead of stopping.

John Ousterhout's A Philosophy of Software Design, Chapter 10, "Define Errors Out Of Existence", explains the design shape: the retrying source masks temporary failures so callers never see them, and the core aggregates every website problem into a review result.

Chapter 10's example is the NFS network file system: when a file server stops responding, the client keeps reissuing the request until the server recovers, instead of reporting an error to every application. Ousterhout argues that retrying in that one low layer is simpler than making every caller handle the failure; the Company Enricher's retrying source follows the same reasoning, but gives up after a few tries so a batch never hangs. None of the three books covers timeouts, backoff, or idempotency; those parts rely on official documentation only.

💡
Key Insight: For every dependency, decide three things in advance: what counts as temporary, how many times to retry, and what the service does when retries run out.

try:

except OSError as error:
    raise WebsiteUnavailable(f"{company_name}: {error}") from error

What's happening: TimeoutError is a kind of OSError, so it must be caught first.

Example 2: Retry with backoff

stage 06 · enricher/adapters/resilience.py
def retry_with_backoff(call, attempts=3, base_delay_seconds=0.2, sleep=time.sleep):
    """Run call(); after a TemporaryWebsiteError wait and try again.

    Waits base_delay, then 2 x base_delay, and so on. Any other error is
    not retried. After the last attempt, raises SourceDown.
    """
    for attempt in range(1, attempts + 1):
        try:
            return call()
        except TemporaryWebsiteError as error:
            if attempt == attempts:
                raise SourceDown(str(error)) from error
            sleep(base_delay_seconds * 2 ** (attempt - 1))

What's happening: sleep is injectable, so tests check the waits without actually waiting.

Example 3: Degraded mode in the core

stage 06 · enricher/core/enrich.py
try:
    page = self._websites.about_page(company.name)
except WebsiteUnavailable:
    return self._needs_review(company, ReviewReason.NO_WEBSITE)
except SourceDown:
    return self._needs_review(company, ReviewReason.SOURCE_DOWN)

def test_a_retried_run_records_each_result_once():
    store = SqliteResultStore()
    fixed = datetime(2026, 1, 5, 9, 0, tzinfo=timezone.utc)
    for _attempt in range(2):  # the whole run is retried after a crash
        enricher = Enricher(SampleWebsiteSource(), KeywordCategoryClassifier(), store, clock=lambda: fixed, run_id="run-2026-01-05")
        enricher.enrich(company("Saltwater Kitchen"))

    assert len(store.history("test:Saltwater Kitchen")) == 1

What's happening: two runs with the same run ID save the company once, because the second insert hits the unique key and does nothing.
