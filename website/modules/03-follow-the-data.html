📚 Core Concepts

Observe: follow one company through the service

Pick one company and follow it: Saltwater Kitchen. The main function in the Module 1 code is suggest_company_category. It receives three things: the company name, a classifier, and a store.

Now read the body line by line and write down what each step touches.

  1. find_official_website("Saltwater Kitchen") looks the name up in SAMPLE_WEB and returns https://saltwaterkitchen.example.
  2. read_about_page(...) searches SAMPLE_WEB again and returns the About-page text.
  3. summarise_business_activity(...) keeps the first sentence: "A seaside restaurant and cafe serving breakfast, lunch and dinner, with catering for events".
  4. classifier.suggest(...) counts category keywords and returns Food & Hospitality with confidence 1.0.
  5. The confidence is at least 0.82, so store.save(...) records the suggestion, and the function returns it.

Notice step 1. SAMPLE_WEB is not a parameter. The function reads it anyway, from a module-level variable. If someone edits that dictionary, the function's answer changes, even though nobody passed it anything new.

Say it plainly: four questions for every function

A function can be fully described by four lists:

QuestionSaltwater Kitchen trace
What comes in?The company name, the classifier, the store, and the SAMPLE_WEB data it reads on its own
What goes out?A suggestion with a category and a confidence, or None
What else changes?The store gains one saved suggestion
What can fail?WebsiteUnavailable when the company is not in the sample web

The bold part is the one people miss. Parameters are easy to see because they sit in the function's first line. Data read from a global variable, a file, a database, a clock, or the network is just as much an input, but you only find it by reading the body.

The same is true for outside changes. The return value is visible at every call. A save, a sent email, or a written file is invisible at the call site unless the name or the docstring tells you.

Name it: inputs, outputs, side effects, dependencies

Programmers have names for these four lists.

  • Inputs and outputs are what goes in and what comes back.
  • A side effect is a change outside the return value, such as saving data.
  • An external dependency is something outside the function that it relies on, such as the website data.
  • A hidden dependency is an external dependency that is not visible in the function's parameters.

John Ousterhout's A Philosophy of Software Design calls the problem behind hidden dependencies an unknown unknown: something you need to know to change the code safely, with nothing in the code telling you that you need to know it (Chapter 2, "The Nature of Complexity"). Chapter 5, "Information Hiding (and Leakage)", adds a second warning. Look at read_about_page: it loops over every page to find a URL that find_official_website already had. Two functions both know how SAMPLE_WEB is shaped. If its shape changes, both must change.

The Pragmatic Programmer's Topic 28, "Decoupling", warns about exactly the SAMPLE_WEB problem. Two of its tips (both p. 136 in the publisher's official list of the book's tips) are "Avoid Global Data" and "If It's Important Enough To Be Global, Wrap It in an API": global data is a hidden input to every function that reads it. Day 5 follows that advice and wraps the website data in one module.

💡
Key Insight: A function's real inputs and outputs are everything it reads and changes, not just its parameters and return value.

🔑 Key Terminology

Input
Any data a function uses to produce its result, whether passed in or read from elsewhere.
Course-authored plain definition
Output
The value a function gives back to its caller.
Course-authored plain definition
Side effect
A change outside the returned value, such as saving data, sending a message, or modifying an input.
Standard software vocabulary; PEP 257 asks docstrings to describe side effects
External dependency
Something outside the function that it relies on, such as a website, file, database, or clock.
Standard software vocabulary; this plain definition is course-authored
Hidden dependency
An external dependency that does not appear in the function's parameters.
Course-authored teaching term
Unknown unknown
Something you must know to change code safely, with no sign in the code that you need to know it.
Paraphrased from John Ousterhout, A Philosophy of Software Design, 2nd ed., Chapter 2
Information leakage
The same design knowledge appearing in more than one module, so a change to it touches all of them.
Paraphrased from John Ousterhout, A Philosophy of Software Design, 2nd ed., Chapter 5

💻 Code Examples

Example 1: A hidden input

stage 01 · enricher.py
def find_official_website(company_name):
    """Return the company's website address, or raise WebsiteUnavailable."""
    page = SAMPLE_WEB.get(company_name)
    if page is None:
        raise WebsiteUnavailable(company_name)
    return page["url"]

What's happening: the only parameter is the name, but the answer also depends on SAMPLE_WEB, a module-level dictionary. Tests that change SAMPLE_WEB change this function's behaviour without calling it differently.

Example 2: Two functions that know the same thing

stage 01 · enricher.py
def read_about_page(website):
    """Return the About-page text published at a website address."""
    for page in SAMPLE_WEB.values():
        if page["url"] == website:
            return page["about"]
    raise WebsiteUnavailable(website)

What's happening: read_about_page searches the same data again, by URL. Both functions know that a page is a dictionary with "url" and "about" keys. That shared knowledge is leakage; Day 5 removes it.
