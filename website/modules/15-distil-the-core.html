Distil the core

📍
Where we are in the story: Week 2 · The code is safe to change. Now you make it speak the business's language.

🎯 Learning Objectives

By the end of today, you will be able to:

  1. Separate the parts of the service that make it valuable from the parts any system needs.
  2. Write a one-paragraph statement of what the core does.
  3. Organise the code so the core can be read on its own.
  4. Enforce the separation with a test.

Plain idea: spend your best design effort on the small part that makes this service worth having, and keep everything else out of its way.

Observe: which parts make the service valuable?

The core is small: a few rules about evidence, confidence, and conflicting sources. Everything else exists to feed it or store what it decides.

Say it plainly: give the core its own room

Stage 04 makes that split visible in the folder structure.

  • enricher/core/ holds categories, the model, the classifier, the policy, the enrich operation, and the ports.py file that says what the core needs from outside.
  • enricher/adapters/ holds the website sources, the partner directory, and the store.

A new developer can read core/ alone and understand what the service decides and why, without seeing a URL, an HTML tag, or a partner code. The package docstring states the purpose in one paragraph, a short domain vision statement:

ℹ️
The Company Enricher suggests a business category for a company from its own website, keeps the evidence, and sends any case a person should judge to review: weak evidence, no website, or sources that disagree.

A test, test_layers.py, reads every file in core/ and fails if any of them imports from adapters/. The separation is no longer a convention someone might forget; it is checked on every run.

Name it: core domain, generic subdomains, segregated core

Eric Evans's Domain-Driven Design, Chapter 15, "Distillation", describes distilling a model to find the core domain: the part that is most valuable and specialised, and that deserves the best people and the most care. Generic subdomains are parts that are needed but not special to the business, and can be handled with off-the-shelf solutions or less effort. The chapter also describes a domain vision statement, a short description of the core's value, and a segregated core, where the core's code is separated from supporting code so it can be understood on its own.

Ousterhout reaches the same conclusion from the design side in Chapter 21, "Decide What Matters", checked in Ousterhout's free 2nd-edition extract. He argues that good design separates what matters from what doesn't, structures the system around what matters, and keeps everything else out of its way. The core/ folder and test_layers.py are that idea applied to the Company Enricher.

💡
Key Insight: If you can't point at the folder that holds your business's reason to exist, nobody can protect it.

🔑 Key Terminology

Core domain
The most valuable and specialised part of the model, where design effort should go first.
Paraphrased from Eric Evans, Domain-Driven Design, Chapter 15
Generic subdomain
A part the system needs that is not special to this business.
Paraphrased from Eric Evans, Domain-Driven Design, Chapter 15
Supporting subdomain
A part specific to this business that exists to support the core.
Standard DDD vocabulary; this plain definition is course-authored
Domain vision statement
A short description of the core domain and the value it brings.
Paraphrased from Eric Evans, Domain-Driven Design, Chapter 15
Segregated core
Core code separated from supporting code so it can be understood alone.
Paraphrased from Eric Evans, Domain-Driven Design, Chapter 15
Port

Example 3: The separation, enforced

stage 04 · tests/test_layers.py
def test_core_does_not_import_adapters():
    offenders = {
        path.name: module
        for path in CORE.glob("*.py")
        for module in imported_modules(path)
        if module.startswith("enricher.adapters")
    }
    assert offenders == {}

What's happening: if anyone imports an adapter into the core, the failure names the file and the import.

🔁 Module 4 · Before / After

Before: after Module 3 the code was safe to change, but spoke developer language: a status string "accepted" that reviewers misread, a separate check for confidence, and no place for a partner's data.

After: the code speaks the reviewers' language. Outcomes and reasons are enums, confidence and evidence are value objects that guard their own rules, companies have identity, the review rule is a named policy, a partner directory is translated at the border, and the core lives in its own folder with a test to keep it there.

stage 04 · enricher/core/policy.py
def decide(self, suggestion, company):
    """Return (Outcome, ReviewReason or None)."""
    if not suggestion.confidence.at_least(self._minimum_confidence):
        return Outcome.NEEDS_REVIEW, ReviewReason.WEAK_EVIDENCE
    if company.directory_hint and company.directory_hint != suggestion.category:
        return Outcome.NEEDS_REVIEW, ReviewReason.CONFLICTING_SOURCES
    return Outcome.SUGGESTED, None
