Plain idea: other code should depend on a function’s promised result, not on the temporary steps inside it.

📚 Core Concepts

Observe: start with a real question

Our service receives a company name, finds the official website, reads its About page, summarises the business activity, and suggests a business category from a short, plain category list.

If another part of the service uses that suggestion, what does it need to know?

01 · IN

What goes in?

A company name, a category classifier, and a place to save results.

02 · OUT

What may come back?

A category suggestion, or None when the evidence is not strong enough.

03 · ELSE

What else happens?

An accepted suggestion is saved; website or classification work may fail.

Say it plainly: read the work once

This function shows the whole flow:

How the work happens today
def suggest_company_category(
    company_name,
    classifier,
    store,
):
    website = find_official_website(
        company_name
    )
    about_text = read_about_page(website)
    activity_summary = (
        summarise_business_activity(
            about_text
        )
    )
    suggestion = classifier.suggest(
        activity_summary
    )

    if suggestion.confidence < 0.82:
        return None

    store.save(company_name, suggestion)
    return suggestion

Some facts affect other code. A weak suggestion returns None. A returned suggestion has already been saved.

Other facts are only today’s method: which service finds the website, which tool reads the page, which model suggests the category, how often the service tries again, and where it saves the result.

Name it: write down the promise

Python lets us place an explanation directly under the function name. This is called a docstring.

Quick reference: four questions

Understand the result before getting lost in the steps used to produce it. Quick test: can you use the function correctly without reading every line inside it?

AskCompany Enricher example
What goes in?A company name, a category classifier, and a place to save results.
What can come back?A category suggestion, or None when evidence is weak.
What else changes?An accepted suggestion is saved before it is returned.
What can fail?The official website or About page may not be found or read.

Do not promise temporary details: a particular search engine, a particular HTML-reading library, private helper names and call order, retry count unless another part of the system must rely on it, or a database or AI vendor that can be replaced.

Two words you do not need yet

Contract appears in broader software-engineering writing as shorthand for promised behaviour. The reviewed Ousterhout chapters do not use it, and this course does not require it.

Callable is official Python vocabulary for anything that can be used with function-call syntax. This lesson uses the narrower word function.

def suggest_company_category(

    Find the official website.
    Read its About page.
    Use classifier to propose a category.

    Return the saved result when its

    Return None when evidence is weaker.

    Raise WebsiteUnavailable when no
    suitable page can be read.
    """
    ...

This explanation states the result, the low-confidence case, the saved change, and one failure. WebsiteUnavailable is a course-authored name for the error raised when no suitable page can be read. It leaves out replaceable details: which service finds the website, which tool reads the page, which model suggests the category, how often it tries again, and where it saves the result.

A useful test checks what other code can observe. It does not check which helper or library was used.

A test that can survive an internal rewrite
def test_weak_suggestion_is_not_saved():
    classifier = classifier_returning(
        category="Manufacturing",
        confidence=0.61,
    )
    store = recording_store()

    result = suggest_company_category(
        "Lantern Lane Bakery",
        classifier,
        store,
    )

    assert result is None
    assert store.saved_suggestions == []

The test checks two visible results: the function returns None, and the store remains unchanged.

Returns a saved category suggestion when confidence meets the threshold.

Transfer: try it elsewhere

⏱️ ~8 min

Choose one function you did not write. Before opening its body, write four lines: input, possible result, other change, and failure. Then read the body to check whether your list is complete.

The Pragmatic Programmer’s Topic 23, “Design by Contract”, frames the same idea as a contract: what a routine expects before it runs, what it guarantees when it finishes, and what stays true throughout.

Its Tip 37 (p. 107 in the publisher’s official tip list) is “Design with Contracts”. This course uses the plainer word promise until the idea is familiar.
