By the end of today, you will be able to:

Plain idea: "good enough" means nothing until you say what you will measure, how, and what number counts as good.

📚 Core Concepts

Observe: three wishes nobody can check

Before the service gets a database, the team writes down what "working well" means. The first draft says:

  1. The service should be accurate.
  2. It shouldn't send too much to review.
  3. It should be fast.

Each line is true and useless. Accurate compared with what? How much review is too much? Fast for whom, measured where? Two people can read the same line and disagree about whether the service passes, which means it cannot guide any decision, including the data design in the next four days.

Say it plainly: indicator, target, method

Each quality becomes three parts: what you measure, the number that counts as good, and how you measure it.

QualityIndicatorTargetHow it is measured
AccurateOf the results the service suggests, the share a person agrees withat least 95%run the labelled sample: 12 companies with a reviewer's decision
Not too much reviewShare of companies that need reviewat most 30%the same run
FastTime to enrich one company, 95th percentileat most 50 ms with the sample website sourcetime.perf_counter() around each call

Notice the choices. Accuracy only counts suggested results, because sending a hard case to review is the service working correctly, not a mistake. Latency uses the 95th percentile: the time that 95% of calls beat. An average hides the slow calls that people actually notice, and one very slow call can hide behind many fast ones.

Today the labelled sample says the service suggests 9 companies, all correctly, and sends 3 to review: precision 100%, review rate 25%. Both meet their targets, with headroom.

The targets go into code, in enricher/quality.py, and a test, test_quality.py, checks them on every run. If a change to the keywords drops precision, the build fails with a number, not an opinion.

Name it: quality attributes, indicators, objectives

Requirements about how well a system works, rather than what it does, are often called quality attributes or non-functional requirements. An indicator is a measured value, such as precision or 95th-percentile latency. A target (in operations work often called an objective) is the value the indicator must meet. A percentile is the value below which a given share of measurements fall.

These terms are standard across the industry; the definitions here are course-authored. For timing, Python's time.perf_counter() gives a clock with the highest available resolution for measuring short durations.

The Pragmatic Programmer's Topic 5, "Good-Enough Software", treats quality as something the people who use the software should help decide, not something developers pick alone. Its Tip 8 (p. 12 in the publisher's official list of the book's tips) is "Make Quality a Requirements Issue": the targets above are that tip written down as numbers.

💡
Key Insight: A quality you cannot measure cannot guide a design decision. Write the indicator, the target, and the method, then test them.

💻 Code Examples

Example 1: The targets, in code

stage 05 · enricher/quality.py
QUALITY_TARGETS = {
    "minimum_precision": 0.95,  # of SUGGESTED results, the share that are right
    "maximum_review_rate": 0.30,  # share of companies sent to a person
    "maximum_p95_latency_ms": 50.0,  # per company, with the sample website source
}

What's happening: the three targets are data, in one place, with a comment saying exactly what each measures.

Example 2: Measuring latency per call

stage 05 · enricher/quality.py
started = time.perf_counter()
result = enricher.enrich(Company(company_id=f"sample:{number}", name=name))
latencies_ms.append((time.perf_counter() - started) * 1000)

What's happening: the timer wraps exactly one enrich call, so the measurement matches the indicator's definition.

Example 3: The targets as a test

stage 05 · tests/test_quality.py
def test_the_service_meets_its_quality_targets():
    report = measure(Enricher(SampleWebsiteSource(), KeywordCategoryClassifier(), InMemoryResultStore()))

    assert report.precision >= QUALITY_TARGETS["minimum_precision"]
    assert report.review_rate <= QUALITY_TARGETS["maximum_review_rate"]
    assert report.p95_latency_ms <= QUALITY_TARGETS["maximum_p95_latency_ms"]

What's happening: a regression in any quality now fails the build with the measured number in the error.
