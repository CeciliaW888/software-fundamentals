📚 Core Concepts

Observe: two ways to ask for a category

The service needs one public operation that the rest of a system will call. Here are two candidates, both able to use the deep modules from Days 5 and 6.

Design A: enrich(company_name) returns a CategorySuggestion when confident, None when not, and raises WebsiteUnavailable when there is no website. This is the Module 1 shape.

Design B: enrich(company_name) always returns an EnrichmentResult with a status ("accepted" or "needs_review"), the suggestion, and the evidence: the URL and the sentence it came from.

Imagine the code that calls each design. A reviewer screen needs to show weak cases with their evidence. With Design A, None carries no evidence and no category, so the screen would have to call the website and classifier again. With Design B, every result already has what the screen needs.

Say it plainly: compare with criteria

Write the criteria down before you choose:

CriterionDesign A: suggestion or NoneDesign B: always a result
What a caller must handlethree cases: value, None, exceptionone type, with a status field
Evidence for reviewerslost on Nonealways included
Room to grownew outcomes need new return shapesnew statuses fit the same type
Cost to builda little less codeone extra small class

Design B wins on everything that callers feel, and loses only on a few lines of code. That trade is almost always worth it, because a module is built once and used many times.

Name it: design it twice, tracer bullets, prototypes

John Ousterhout's A Philosophy of Software Design, Chapter 11, "Design it Twice" (to verify against book), recommends considering at least two radically different designs for each major decision, and comparing them on what matters most, such as the simplicity of the interface. Even when the first idea wins, the comparison shows you why.

The Pragmatic Programmer offers two ways to test a design cheaply. Topic 12, "Tracer Bullets" (to verify against book) describes building a thin version that runs end to end through every part of the system, then filling it in. Topic 13, "Prototypes and Post-it Notes" (to verify against book) describes throwaway experiments that answer one question and are then discarded.

The Module 2 project has a tracer bullet: python -m enricher runs every sample company through the real website module, classifier, and store, and prints one line each. It is small, but it is real code you keep and grow.

Three tips in the publisher's official list of the book's tips sum up today's methods: Tip 20 (p. 51), "Use Tracer Bullets to Find the Target", Tip 21 (p. 57), "Prototype to Learn", and Tip 68 (p. 218), "Build End-To-End, Not Top-Down or Bottom Up".

💡
Key Insight: Write the caller's code for each design before choosing; the better interface is the one that makes calling code simpler.

🔑 Key Terminology

Design it twice
Considering two or more substantially different designs before choosing one.
Paraphrased from John Ousterhout, A Philosophy of Software Design, 2nd ed., Chapter 11 (to verify against book)
Tracer bullet
A thin, working path through every layer of a system, kept and filled in over time.
Paraphrased from Thomas and Hunt, The Pragmatic Programmer, 20th Anniversary Edition, Topic 12, "Tracer Bullets" (to verify against book)
Prototype
A throwaway experiment built to answer one specific question.
Paraphrased from Thomas and Hunt, The Pragmatic Programmer, 20th Anniversary Edition, Topic 13, "Prototypes and Post-it Notes" (to verify against book)
Result object
A value that always comes back from an operation and describes what happened.
Course-authored plain definition
Status
A field on a result that says which outcome happened, such as accepted or needs review.
Course-authored plain definition

Example 2: The public operation

stage 02 · enricher/enricher.py
def enrich(self, company_name):
    """Suggest a category for one company, with its evidence.

    Always returns an EnrichmentResult. Its status is "accepted" when
    confidence reaches the minimum, and the result is then saved;
    otherwise it is "needs_review" and nothing is saved.
    Raises WebsiteUnavailable when no About page can be read.
    """
    page = self._websites.about_page(company_name)
    suggestion = self._classifier.suggest(page.main_activity)
    accepted = suggestion.confidence >= self._minimum_confidence
    result = EnrichmentResult(
        company_name=company_name,
        status=ACCEPTED if accepted else NEEDS_REVIEW,
        suggestion=suggestion,
        evidence_url=page.url,
        evidence_text=page.main_activity,
    )
    if accepted:
        self._store.save(result)
    return result

What's happening: one missing website still raises an exception here. That is a deliberate loose end: Day 8 decides what that failure should mean.
