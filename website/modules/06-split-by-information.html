Split by information, not length

🎯 Learning Objectives

By the end of today, you will be able to:

  1. Decide whether two pieces of code belong together by asking what knowledge they share.
  2. Compare a short-function design with a deep-function design of the same classifier.
  3. Recognise duplicated knowledge, not just duplicated text.

Plain idea: keep code together when it shares knowledge, and apart when it does not, whatever the line count says.

📚 Core Concepts

Observe: one classifier, two shapes

The project holds two versions of the same classifier, and a test proves they give identical answers for every sample company.

The first, in exercises/day06_short_functions.py, is split into six short functions: tokenize, count_hits, total_hits, best_category, confidence_for, and suggest_category. Each one is two or three lines.

The second, KeywordCategoryClassifier.suggest in classifier.py, is one function of about ten lines.

Read both and ask a different question from "which is shorter?". Ask: to change how confidence is calculated, how many functions must I read? In the short version, confidence depends on count_hits, total_hits, and confidence_for, and the zero-hit rule sits in a fourth function. In the deep version, all of that is on one screen.

Say it plainly: split by what code knows

A rule that keeps showing up: code that shares knowledge should live together. The six short functions all share one piece of knowledge, "a hit count per category decides the answer", so splitting them does not separate anything. It only makes the reader jump between them and makes callers responsible for the order.

Now the opposite case. The classifier knows nothing about websites, and the website module knows nothing about keywords. That split is worth keeping: you can change one without reading the other.

Duplication follows the same rule. In the Module 1 code, predict_proba returned probabilities in CATEGORIES order and suggest turned a position back into a name. The text was not duplicated, but the knowledge "probabilities follow list order" was needed in two places. The Module 2 classifier counts hits in a dictionary keyed by category, so no code has to know about positions at all.

Name it: better together, DRY, orthogonality

John Ousterhout's A Philosophy of Software Design, Chapter 9, "Better Together Or Better Apart?", argues that pieces of code should be combined when they share information, when combining simplifies the interface, or when it removes duplication. He also warns against splitting a method only to make it shorter, because readers then have to understand several pieces at once.

The Pragmatic Programmer states the duplication rule as DRY in Topic 9, "DRY - The Evils of Duplication": each piece of knowledge in a system should be expressed in exactly one place that everything else defers to. The authors stress that DRY is about knowledge and intent, not just copied text.

The same book's Topic 10, "Orthogonality" describes the other half: two parts are orthogonal when changing one does not affect the other. The classifier and the website module are orthogonal; the six short functions are not.

The publisher's free excerpt of Topic 9 makes the knowledge point in detail: the acid test for duplication is whether one change in the world forces edits in more than one place, and two pieces of code that merely look alike are not duplication if they could change for different reasons. Ousterhout's free extract also contains section 9.8, his comparison with Clean Code: he agrees that very long functions are hard to read, but argues that splitting purely by length pushes readers to understand several functions at once.

💡
Key Insight: The right question is not "is this function too long?" but "what does this code know, and who else knows it?".

🔑 Key Terminology

DRY
Each piece of knowledge in a system should be expressed in exactly one authoritative place.
Paraphrased from Thomas and Hunt, The Pragmatic Programmer, 20th Anniversary Edition, Topic 9, "DRY - The Evils of Duplication", checked in the publisher's free excerpt
Orthogonality
Two parts are orthogonal when a change to one does not affect the other.
Paraphrased from Thomas and Hunt, The Pragmatic Programmer, 20th Anniversary Edition, Topic 10, "Orthogonality"
Duplicated knowledge
The same fact or rule needed in more than one place, even if the code text differs.
Course-authored plain definition, following The Pragmatic Programmer's DRY topic
Shared information
Knowledge two pieces of code must both have, which is a reason to keep them together.
Paraphrased from John Ousterhout, A Philosophy of Software Design, 2nd ed., Chapter 9
Dictionary
A Python mapping from keys to values, such as category to hit count.
Official Python vocabulary (Python tutorial: dictionaries)

💻 Code Examples

Example 1: Six short functions

stage 02 · exercises/day06_short_functions.py
def total_hits(hits):
    return sum(hits.values())


def best_category(hits):
    return max(hits, key=hits.get)


def confidence_for(hits, category):
    return hits[category] / total_hits(hits)


def suggest_category(text):
    hits = count_hits(tokenize(text))
    if total_hits(hits) == 0:
        return OTHER, 0.0
    category = best_category(hits)
    return category, confidence_for(hits, category)

What's happening: each function is tiny, but to understand suggest_category you must read four others, and the zero-hit rule is separated from the confidence rule it protects.

Example 2: One deep function

stage 02 · enricher/classifier.py
class KeywordCategoryClassifier:
    """Suggests the category whose keywords appear most often.

    Confidence is the share of keyword hits that belong to the winning
    category. Text with no keywords is "Other" with confidence 0.0.
    """

    def suggest(self, text):
        words = re.findall(r"[a-z]+", text.lower())
        hits = {
            category: sum(1 for word in words if word in keywords)
            for category, keywords in CATEGORY_KEYWORDS.items()
        }
        total_hits = sum(hits.values())
        if total_hits == 0:
            return CategorySuggestion(OTHER, 0.0)
        best = max(hits, key=hits.get)
        return CategorySuggestion(best, hits[best] / total_hits)

What's happening: the whole rule, including the zero-hit case, reads top to bottom. The docstring states the rule in one sentence, which is only possible because the rule lives in one place.

Example 3: The test that keeps the comparison honest

stage 02 · tests/test_designs_agree.py
@pytest.mark.parametrize("about", [page["about"] for page in SAMPLE_WEB.values()])
def test_both_designs_suggest_the_same_category(about):
    deep = KeywordCategoryClassifier().suggest(about)
    assert suggest_category(about) == (deep.category, deep.confidence)

What's happening: both designs are correct, so the choice between them is about who has to understand what, not about behaviour.

Hint
