Choose a data model from access patterns

Plain idea: design storage from the questions you will ask of it, not from the objects you happen to have.

📚 Core Concepts

Observe: results disappear, and reviewers can't find their work

The Module 4 store keeps results in a Python list. Two problems show up as soon as the review team uses it. First, everything is lost when the program stops. Second, the store only keeps suggested results, but the reviewers' whole job is the other kind: the companies that need review. There is nowhere to ask "what's waiting for me?".

So before choosing a database, write down the questions, the access patterns:

  1. Record every enrichment result, with its outcome, reason, suggestion, and evidence.
  2. Get the latest result for one company.
  3. List the results waiting for review, oldest first.
  4. Show the full history of one company's results.

Pattern 1 changes the service's behaviour: Enricher now records every result, not only suggested ones. That is a deliberate change, made because a real user need required it, and the docstring and a test say so.

Say it plainly: shape the data for the questions

Each pattern hints at a shape.

  • Patterns 2 and 4 ask "everything about one company", so results need a company ID.
  • Pattern 3 asks "all results with outcome needs review, by time", across all companies, so outcome and time should be plain columns that can be filtered and sorted.
  • Companies have a name that can change (Day 13), so they get their own small table, and results refer to them by ID.

That gives two tables: companies and results. Each result row holds its outcome, reason, category, confidence, evidence, and the time it was checked.

Now compare other shapes for the same data:

ShapeHow it would store a resultFits our patterns?
Relational (tables, rows, columns)one row per result, columns for each fieldyes: all four patterns are simple queries
Document (one JSON document per company)each company's document holds a list of its resultspatterns 2 and 4 are easy; pattern 3 must search inside every document
Graph (nodes and edges)companies, categories, and results as nodes, linked by edgesstrong for "which companies are related?"; nobody asks that here

The relational shape wins, not because it is always best, but because these four questions are simple filters and sorts over one kind of record. PostgreSQL can also store JSON inside a relational table, which is useful when part of a record has no fixed shape.

SQLite is enough for this service: it is a database in a single file, built into Python's standard library through the sqlite3 module. The adapter SqliteResultStore implements the same save method as the in-memory store, plus one method per access pattern.

Name it: access patterns, schema, relational model

An access pattern is a question the system will repeatedly ask of its data. A schema is the declared structure of a database: its tables, columns, and their types. A relational database stores data as rows in tables and answers questions with SQL; SQLite and PostgreSQL are both relational. A primary key is the column that identifies each row; a foreign key is a column whose values must match a primary key in another table.

Evans's free DDD Reference describes a repository as the way a model offers query access to stored objects in the ubiquitous language, so database details don't leak into the domain code. SqliteResultStore plays that role: its methods are named for reviewers' questions, such as review_queue, and only the adapter knows about SQL. The same chapter, Chapter 6, "The Life Cycle of a Domain Object", has a section on designing objects for relational databases. When a database exists to store the model's objects, Evans advises keeping the tables close to the model, using the same names, and keeping other programs from writing to it directly, because they could break rules the objects enforce.

💡
Key Insight: List the queries first. A schema that makes your most frequent queries simple is a good schema for you, whatever is fashionable.

🔑 Key Terminology

Access pattern
A question the system repeatedly asks of its stored data.
Course-authored plain definition
Schema
The declared structure of a database: tables, columns, and their types.
Standard database vocabulary; see SQLite: CREATE TABLE
Relational database
A database that stores rows in tables and is queried with SQL.
Standard database vocabulary; this plain definition is course-authored
Primary key
The column or columns that uniquely identify each row in a table.
Official SQLite vocabulary (CREATE TABLE)
Foreign key
A column whose values must match a key in another table.
Official SQLite vocabulary (foreign keys)
Document model
Storing each record as a self-contained document, such as JSON.
Standard database vocabulary; see PostgreSQL: JSON types
Repository
An object that gives the model query access to stored objects in the model's own language, hiding the database details.
Paraphrased from Eric Evans, Domain-Driven Design, Chapter 6

💻 Code Examples

Example 1: The tables, shaped by the patterns

stage 05 · enricher/adapters/migrations.py
CREATE TABLE companies (
    company_id TEXT PRIMARY KEY,
    name       TEXT NOT NULL
);
CREATE TABLE results (
    result_id        INTEGER PRIMARY KEY,
    company_id       TEXT NOT NULL REFERENCES companies (company_id),
    outcome          TEXT NOT NULL,
    reason           TEXT,
    category         TEXT,
    confidence       REAL,
    evidence_url     TEXT,
    evidence_excerpt TEXT,
    checked_at       TEXT NOT NULL
);

What's happening: every column a pattern filters or sorts on is a plain column. Fields that only some results have, such as reason, allow NULL.

Example 2: One method per access pattern

stage 05 · enricher/adapters/sqlite_store.py
def review_queue(self, limit=20):
    """Access pattern 3: results waiting for a person, oldest first."""
    return self.connection.execute(
        "SELECT * FROM results WHERE outcome = ? ORDER BY checked_at LIMIT ?",
        (Outcome.NEEDS_REVIEW.value, limit),
    ).fetchall()

What's happening: the ? placeholders let sqlite3 pass values safely, so data is never pasted into SQL text.

Example 3: The behaviour change, stated

stage 05 · tests/test_scenarios.py
def test_every_result_is_recorded_for_reporting_or_review(enricher, store):
    suggested = enricher.enrich(company("Saltwater Kitchen"))
    needs_review = enricher.enrich(company("Lantern Lane Bakery"))
    assert store.saved_results == [suggested, needs_review]

What's happening: the old test said "only suggested results are saved". The requirement changed, so the test changed with it, on purpose.
