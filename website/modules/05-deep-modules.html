📚 Core Concepts

Observe: what a caller must know today

In the Module 1 code, getting a company's activity takes three calls in a fixed order:

  1. find_official_website(company_name) returns a URL.
  2. read_about_page(website) takes that URL and returns text.
  3. summarise_business_activity(about_text) returns the first sentence.

Every caller must know all three names, their order, and that a URL passes from step 1 to step 2. The URL is not useful to the caller; it only exists to be handed back. And as Day 3 showed, two of the helpers both know how the website data is shaped.

Say it plainly: cost versus benefit of a module

Think of any piece of code as a box. The outside of the box is what callers must learn: names, parameters, rules, and failures. The inside is the work the box does for them.

A box is worth having when the inside is large and the outside is small. The three website helpers are the opposite: each one does very little, and together they ask the caller to learn a lot.

The Module 2 code has one box instead: CompanyWebsites. A caller asks one question, "what does this company say about itself?", and gets an AboutPage back. How the website is found, how the page is read, and where the data lives are all inside. Even "the first sentence states the main activity" is now a property of the page, main_activity, instead of a separate step every caller must remember.

Name it: deep modules, shallow modules, pass-through methods

John Ousterhout's A Philosophy of Software Design uses module for any unit with an interface and an implementation, from a function to a service (Chapter 4, "Modules Should Be Deep" (to verify against book)). A deep module offers powerful functionality through a simple interface. A shallow module has an interface that is complicated relative to what it does, so it adds more to learn than it saves.

Chapter 7, "Different Layer, Different Abstraction" (to verify against book), names a common shallow pattern: the pass-through method, which does little except hand its arguments to another method. Chapter 8, "Pull Complexity Downwards" (to verify against book), gives the direction of the fix: it is better for the module to absorb complexity than for every caller to deal with it.

The main_activity property is a small example of pulling complexity down. The rule "use the first sentence" now lives in one place, inside the module that owns the page.

Ousterhout's Chapter 6, "General-Purpose Modules are Deeper", checked in Ousterhout's free 2nd-edition extract, adds a second test of a good interface. He recommends making modules somewhat general-purpose: the implementation does what today's callers need, but the interface is not tied to one particular use. CompanyWebsites.about_page passes that test. It answers a general question about any company, and says nothing about keywords or categories, so a classifier, a report, or a reviewer screen can all use it.

💡
Key Insight: Judge a module by how much it saves its callers, not by how short it is.

🔑 Key Terminology

Module
A unit of code with an interface and an implementation, from a function to a whole service.
Paraphrased from John Ousterhout, A Philosophy of Software Design, 2nd ed., Chapter 4 (to verify against book)
Interface
Everything someone working elsewhere must know to use the module.
Paraphrased from John Ousterhout, A Philosophy of Software Design, 2nd ed., Chapter 4 (to verify against book)
Deep module
A module that provides powerful functionality behind a simple interface.
Paraphrased from John Ousterhout, A Philosophy of Software Design, 2nd ed., Chapter 4 (to verify against book)
Shallow module
A module whose interface is complicated compared with the functionality it provides.
Paraphrased from John Ousterhout, A Philosophy of Software Design, 2nd ed., Chapter 4 (to verify against book)
Pass-through method
A method that does little except pass its arguments to another method.
Paraphrased from John Ousterhout, A Philosophy of Software Design, 2nd ed., Chapter 7 (to verify against book)
Property
A Python attribute whose value is computed by a method each time it is read.
Official Python vocabulary (built-in functions: property)
Somewhat general-purpose
A module whose functionality meets today's needs while its interface is general enough for several uses.
Paraphrased from John Ousterhout, A Philosophy of Software Design, 2nd ed., Chapter 6, checked in the author's free extract

💻 Code Examples

Example 1: Before, three helpers in a fixed order

stage 01 · enricher.py
def summarise_business_activity(about_text):
    """Return the first sentence, which usually states the main activity."""
    return about_text.split(".")[0]

What's happening: together with find_official_website and read_about_page from Day 3, this is the third step a caller must remember. Each helper is short; the interface of the trio is long.

Example 2: After, one deep module

stage 02 · enricher/website.py
@dataclass(frozen=True)
class AboutPage:
    url: str
    text: str

    @property
    def main_activity(self):
        """The first sentence, which usually states what the business does."""
        return self.text.split(".")[0]


class CompanyWebsites:
    """One call answers "what does this company say about itself?"."""

    def __init__(self, pages=SAMPLE_WEB):
        self._pages = pages

    def about_page(self, company_name):
        page = self._pages.get(company_name)
        if page is None:
            raise WebsiteUnavailable(company_name)
        return AboutPage(url=page["url"], text=page["about"])

What's happening: callers learn one method and one result type. The page data is passed in once, which also removes Day 3's hidden global: a test can hand CompanyWebsites any pages it likes. The URL is still kept, inside AboutPage, because it is useful later as evidence.

Example 3: The caller now

stage 02 · enricher/enricher.py
page = self._websites.about_page(company_name)
suggestion = self._classifier.suggest(page.main_activity)

What's happening: two lines replace the three-step chain, and neither line mentions URLs or data shapes.
