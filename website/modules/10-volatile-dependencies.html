📚 Core Concepts

Observe: what is likely to change

The volatile ones are the website source, the clock, and the store. In stage 02, CompanyWebsites reads sample data directly, and nothing in the code shows how a real website would fit in.

Say it plainly: a small door at the edge

Stage 03 draws a line. The core of the service, Enricher, only ever asks one question of a website source: give me the About page for this company name, or tell me there isn't one. That question is written down as WebsiteSource. Any object with an about_page method that returns an AboutPage or raises WebsiteUnavailable can be used.

Two objects answer it today:

  • SampleWebsiteSource reads the made-up sample companies. Tests and the tracer bullet use it.
  • HttpWebsiteSource fetches a real page, strips the HTML to text, and turns network errors into WebsiteUnavailable. It is the only code that knows about URLs, HTML, and timeouts.

The clock gets the same treatment. Enricher takes a clock argument, a function returning the current time, with the real clock as the default. Tests pass a function that always returns the same moment.

The HTTP adapter has one more door inside it: the fetch function. Its tests pass a fake fetch that returns a fixed HTML string or raises TimeoutError, so the adapter's own logic is tested without the network.

Name it: boundaries, adapters, protocols, dependency injection

A boundary is where your code meets something it does not control. An adapter is the code at that boundary that translates between the outside world's terms and yours. In Python, a typing.Protocol describes the methods an object must have without requiring it to inherit from anything. Passing a dependency in, instead of letting the code fetch it itself, is called dependency injection.

John Ousterhout's A Philosophy of Software Design gives the reasons in Chapter 5, "Information Hiding (and Leakage)" (to verify against book): details such as HTML parsing and timeouts are hidden in one module. Chapter 7, "Different Layer, Different Abstraction" (to verify against book), explains why each layer should speak its own vocabulary: the core talks about About pages, the adapter about URLs and bytes. Chapter 8, "Pull Complexity Downwards" (to verify against book), is why the adapter, not every caller, deals with network errors.

Ousterhout's Chapter 6, "General-Purpose Modules are Deeper", checked in Ousterhout's free 2nd-edition extract, explains why WebsiteSource is shaped the way it is: the interface is general enough that sample data, real HTTP, and a test fake all fit behind it, while each implementation stays as simple as today's need. The Pragmatic Programmer's Topic 28, "Decoupling" (to verify against book), gives the same direction as Tip 48 (p. 136 in the publisher's official list of the book's tips): if something outside the code is important enough to share, put an API in front of it.

💡
Key Insight: Hide each volatile thing behind the smallest interface the core needs, and the core never changes when it does.

💻 Code Examples

Example 1: What the core needs, written down

stage 03 · enricher/website.py
class WebsiteSource(Protocol):
    def about_page(self, company_name: str) -> AboutPage:
        """Return the company's About page or raise WebsiteUnavailable."""

What's happening: this is the whole door. Anything with this method can be a website source, including a test's fake.

Example 2: The only code that knows about HTTP

stage 03 · enricher/website.py
def about_page(self, company_name):
    url = self._about_urls.get(company_name)
    if url is None:
        raise WebsiteUnavailable(company_name)
    try:
        html = self._fetch(url, self._timeout_seconds)
    except OSError as error:
        raise WebsiteUnavailable(f"{company_name}: {error}") from error
    extractor = _TextExtractor()
    extractor.feed(html)
    text = " ".join(part for part in extractor.parts if part)
    if not text:
        raise WebsiteUnavailable(f"{company_name}: About page has no text")
    return AboutPage(url=url, text=text)

What's happening: network errors (Python's TimeoutError is a kind of OSError) become the core's own WebsiteUnavailable, and HTML becomes plain text. The core never sees an OSError or a tag.

Example 3: Testing the adapter with no network

stage 03 · tests/test_http_source.py
def test_network_error_becomes_website_unavailable():
    def fetch(url, timeout_seconds):
        raise TimeoutError("timed out")

    with pytest.raises(WebsiteUnavailable):
        HttpWebsiteSource(URLS, fetch=fetch).about_page("Saltwater Kitchen")

What's happening: the fake fetch simulates a timeout instantly, so the test is fast and never touches the internet.
