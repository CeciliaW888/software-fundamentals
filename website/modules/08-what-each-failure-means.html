📚 Core Concepts

Observe: what can go wrong today

Run the Module 2 tracer bullet with one extra company, Ghost Gum Traders, which has no website. The whole batch stops with a WebsiteUnavailable traceback. Ten good results are lost because of one missing website.

List every way the service can go wrong:

  1. A company has no website, or the page cannot be read.
  2. The About page has no category keywords.
  3. A classifier returns a confidence of 1.7, which is impossible.
  4. Saving a result fails.

These are not the same kind of problem. The first two happen every day with real companies. The third means the code is wrong. The fourth means something outside the service is broken.

Say it plainly: four things you can do with a failure

For each failure you have four choices.

  • Prevent it. Change the rules so the situation is not an error. No keywords is not an error; it just means the category is Other with confidence 0.0, which already goes to review.
  • Hide it. Handle it inside the module so callers never see it. "No website" becomes a result with status needs_review and reason no_website.
  • Combine it. Handle many similar failures in one place. Every review reason flows through the same result type, so a reviewer screen handles them all the same way.
  • Report it. Stop and tell someone. An impossible confidence means a bug, so the service raises ValueError immediately rather than saving nonsense.

Store failures are left to report themselves: hiding a failed save would lose data silently.

Name it: define errors out of existence, crash early

John Ousterhout's A Philosophy of Software Design, Chapter 10, "Define Errors Out Of Existence" (to verify against book), argues that exceptions add complexity to every caller, and that the best way to reduce it is to design so that fewer exceptions are needed. He describes defining errors out of existence, exception masking (handling a condition at a low level so higher levels never see it), and exception aggregation (handling many exceptions in one place). He also notes that some errors are best handled by simply crashing, when recovery is not worth the complexity.

The Pragmatic Programmer makes the crash case in Topic 24, "Dead Programs Tell No Lies" (to verify against book): when code finds something that should be impossible, stopping usually does less harm than carrying on with bad data. Topic 25, "Assertive Programming" (to verify against book) recommends checking for the impossible in code, so the check fails loudly if it ever happens. In this service, check_confidence plays that role with an explicit ValueError, which unlike assert cannot be switched off.

Two tips in the publisher's official list of the book's tips name the rule directly: Tip 38 (p. 113), "Crash Early", and Tip 39 (p. 115), "Use Assertions to Prevent the Impossible".

💡
Key Insight: Expected situations become normal results; impossible situations stop the program. Do not mix the two.

🔑 Key Terminology

Exception
A Python object that signals an error and interrupts normal flow until something handles it.
Official Python vocabulary (tutorial: errors and exceptions)
Exception masking
Handling an exceptional condition at a low level so higher levels never see it.
Paraphrased from John Ousterhout, A Philosophy of Software Design, 2nd ed., Chapter 10 (to verify against book)
Exception aggregation
Handling many exceptions with one piece of code instead of many.
Paraphrased from John Ousterhout, A Philosophy of Software Design, 2nd ed., Chapter 10 (to verify against book)
Crash early
Stopping as soon as the code finds an impossible state, instead of continuing with bad data.
Paraphrased from Thomas and Hunt, The Pragmatic Programmer, 20th Anniversary Edition, Topic 24, "Dead Programs Tell No Lies" (to verify against book)
Review reason
Why a result needs a person: weak evidence or no website.
Course domain term

💻 Code Examples

Example 1: "No website" becomes a result

stage 03 · enricher/enricher.py
try:
    page = self._websites.about_page(company_name)
except WebsiteUnavailable:
    return self._needs_review(company_name, NO_WEBSITE)

What's happening: the exception is masked inside enrich. Callers get a normal EnrichmentResult with status needs_review and reason no_website, and the batch carries on.

Example 2: An impossible value stops the program

stage 03 · enricher/enricher.py
def check_confidence(confidence):
    """A confidence outside 0..1 is a bug in a classifier: stop at once."""
    if not 0.0 <= confidence <= 1.0:
        raise ValueError(f"confidence must be between 0 and 1, got {confidence!r}")

What's happening: enrich calls this on every suggestion before using it. A broken classifier is reported loudly instead of producing confident nonsense.

Example 3: An error defined out of existence

stage 03 · enricher/classifier.py
if total_hits == 0:
    return CategorySuggestion(OTHER, 0.0)

What's happening: text without keywords is a normal answer, Other with zero confidence, and the review rule handles it like any other weak suggestion.
