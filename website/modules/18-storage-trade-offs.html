Plain idea: an index is a sorted shortcut to the rows you ask for most; it speeds up those reads and makes every write do a little more work.

📚 Core Concepts

Observe: ask the database how it will answer

The review queue query is:

text
SELECT * FROM results WHERE outcome = ? ORDER BY checked_at LIMIT ?

With a dozen sample rows it is instant. With a year of results it might not be. Instead of guessing, ask the database: in SQLite, putting EXPLAIN QUERY PLAN in front of a query returns the plan it would use, without running it.

On the Day 17 schema, the plan says SCAN results, plus a step that sorts the matching rows by time. Scan means SQLite will read every row in the table, check each one's outcome, then sort the matches. The work grows with the size of the whole table, not with the size of the queue.

Say it plainly: a sorted shortcut, with a cost

An index is a separate, sorted copy of some columns, with a pointer back to each row. The review queue filters on outcome and sorts on checked_at, so an index on (outcome, checked_at) stores exactly what the query needs, in exactly the order it needs it.

After migration 2 adds that index, the plan becomes:

SEARCH results USING INDEX results_review_queue (outcome=?)

Search means SQLite jumps straight to the needs review entries, already in time order, and stops after LIMIT rows. No full scan, and no separate sort.

Indexes are not free:

CostWhy
Slower writesevery insert must also update the index
More storagethe index is a second copy of those columns
Something to maintainthe planner only uses it if the query matches its columns

So you add an index for a frequent, important query, not for every column. The review queue is the reviewers' main screen, which earns it an index; nobody yet sorts results by confidence, so that column gets none.

The project's test test_query_plan.py checks both plans: a scan without the index, a search with it. If someone later changes the query or drops the index, the test fails instead of the screen quietly getting slower.

Name it: index, query planner, scan, search

A database's query planner chooses how to execute each query. A full table scan reads every row; an index search uses an index to find matching rows directly. A composite index covers more than one column, and its column order matters: SQLite's documentation explains that the planner can use the leftmost columns of an index for equality tests and the next column for sorting.

PostgreSQL works the same way in principle, with its own EXPLAIN command and plan format, and documents several index types beyond the default.

The Pragmatic Programmer's Topic 39, "Algorithm Speed" (to verify against book), gives the reasoning behind the index: a scan's work grows in step with the table, while an index lookup grows far more slowly. Its Tips 63 (p. 207), "Estimate the Order of Your Algorithms", and 64 (p. 208), "Test Your Estimates", in the publisher's official list of the book's tips, are the two halves of this lesson: reason about growth, then check with the query plan.

💡
Key Insight: Don't guess where time goes in a query; ask the planner, add the index the plan needs, and pin the plan in a test.

🔑 Key Terminology

Index
A separate sorted structure that lets the database find rows by some columns without reading the whole table.
Official SQLite vocabulary (CREATE INDEX)
Query plan
The steps the database will take to answer a query.
Official SQLite vocabulary (EXPLAIN QUERY PLAN)
Query planner
The part of the database that chooses a query plan.
Official SQLite vocabulary (query planning)
Full table scan
Reading every row of a table to answer a query.
Standard database vocabulary; this plain definition is course-authored
Composite index
An index on more than one column, used left to right.
Standard database vocabulary; see SQLite query planning
Write amplification
Extra work each write must do, such as updating indexes.
Standard database vocabulary; this plain definition is course-authored

💻 Code Examples

Example 1: The index, as a migration

stage 05 · enricher/adapters/migrations.py
CREATE INDEX results_review_queue
    ON results (outcome, checked_at);

What's happening: column order follows the query: filter by outcome first, then read in checked_at order.

Example 2: Asking for the plan

stage 05 · tests/test_query_plan.py
def plan(connection):
    rows = connection.execute("EXPLAIN QUERY PLAN " + QUEUE_QUERY, ("needs_review", 20)).fetchall()
    return " | ".join(row[-1] for row in rows)

What's happening: the last column of each plan row is SQLite's description of that step.

Example 3: Pinning both plans

stage 05 · tests/test_query_plan.py
def test_without_the_index_the_queue_query_scans_every_row():
    connection = sqlite3.connect(":memory:")
    migrate(connection, target=1)
    assert "SCAN results" in plan(connection)


def test_with_the_index_the_queue_query_searches_it():
    connection = sqlite3.connect(":memory:")
    migrate(connection, target=len(MIGRATIONS))
    assert "SEARCH results USING INDEX results_review_queue (outcome=?)" in plan(connection)

What's happening: the first test proves the index is what makes the difference; the second guards it.

✏️ Hands-On Exercises

Exercise 1 · Check (⏱️ ~3 min)

Q1: What does SCAN results in a plan mean?

Q2: Why is the index on (outcome, checked_at) and not (checked_at, outcome)?

Q3: What is the main cost of adding an index?

Exercise 2 · Change: index the history query (⏱️ ~20 min)

Goal: Decide on an index from a plan, not a guess.

Instructions:

  1. Write a test like plan() for the history query: SELECT * FROM results WHERE company_id = ? ORDER BY checked_at, result_id.
  2. Run it against the current schema and read the plan.
  3. Decide whether an index on (company_id, checked_at) is worth it, given how often reviewers open a company's history.
  4. If yes, add it as a new migration (never edit an old one) and update the test to expect a search.
Hint

Append a new SQL string to MIGRATIONS. Day 19 explains why released migrations are never edited.

Exercise 3 · Transfer: read one plan (⏱️ ~10 min)

In any database you use, run EXPLAIN (PostgreSQL) or EXPLAIN QUERY PLAN (SQLite) on one frequent query. Write down whether it scans or searches, and which index it uses.
