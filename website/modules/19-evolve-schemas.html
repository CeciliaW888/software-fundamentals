📚 Core Concepts

Observe: a column the reviewers want

Reviewers ask a new question: "which version of the classifier made this suggestion?". When the keywords change, they want to know which old results were made with the old keywords. That needs a new column, classifier_version.

A database in use already has rows, and possibly more than one program reading it: the enrichment batch, a reviewer screen, a weekly report. They are not all deployed at the same moment. For a while, old code and new code run against the same database.

If the change renames or removes a column, the old programs break the moment it lands. If it only adds something that old programs never ask for, they keep working.

Say it plainly: numbered steps, expand before contract

The project keeps every schema change in one list, MIGRATIONS, in order. Step 1 is the Day 17 tables; step 2 is the Day 18 index; step 3 adds the new column. The database remembers how many steps it has applied, and migrate() applies only the ones after that. Running it twice changes nothing.

Two rules keep this safe:

  1. Never edit a released step. Some databases already ran it. Fix mistakes with a new step.
  2. Expand first, contract later. Add new columns or tables in one release (expand). Remove or rename old ones only in a later release, once no running code uses them (contract).

Step 3 is expand-only: ALTER TABLE results ADD COLUMN classifier_version TEXT. The column allows NULL, so rows written before it existed are still valid. The old reader, which names its columns explicitly, never notices. The new reader handles the old rows by treating NULL as 'unknown'.

A reader that uses SELECT * and expects an exact number of columns would break here. Naming columns explicitly is part of making evolution safe.

Name it: migrations, user_version, expand and contract

A migration is one numbered, ordered change to a database schema. SQLite stores a free integer in each database file, read and written with PRAGMA user_version, which this project uses as the migration number. SQLite's ALTER TABLE ... ADD COLUMN adds a column to an existing table; its documentation lists the restrictions, such as the new column not being allowed a primary key.

Expand and contract is a common name for doing compatible changes first and removing the old shape later. PostgreSQL documents the same kinds of ALTER TABLE operations, and the same rule applies there.

The books do not teach database migrations, but two of them explain why they need care. Evans's Domain-Driven Design, Chapter 6, "The Life Cycle of a Domain Object", observes that serious data migration problems discourage frequent schema changes, and that a model and a schema allowed to drift apart quickly become hard to follow. The Pragmatic Programmer supplies the attitude behind expand and contract. Its Tip 18 (p. 48 in the publisher's official list of the book's tips) is "There Are No Final Decisions", and Topic 27, "Don't Outrun Your Headlights", available as the publisher's free excerpt on the book page, argues for small steps whose effects you can check before taking the next. Each migration is one such step, and expand-only steps keep the previous version runnable.

💻 Code Examples

Example 1: An expand-only step

stage 05 · enricher/adapters/migrations.py
ALTER TABLE results ADD COLUMN classifier_version TEXT;

Example 2: Applying only what is missing

stage 05 · enricher/adapters/migrations.py
def schema_version(connection):
    return connection.execute("PRAGMA user_version").fetchone()[0]


def migrate(connection, target=len(MIGRATIONS)):
    """Apply every step between the database's version and target."""
    current = schema_version(connection)
    for version in range(current + 1, target + 1):
        with connection:
            connection.executescript(MIGRATIONS[version - 1])
            connection.execute(f"PRAGMA user_version = {version}")

What's happening: each step and its version bump happen together, so a database is never left half-way through a step without knowing it.

Example 3: Old and new readers, tested together

stage 05 · tests/test_migrations.py
OLD_READER = "SELECT company_id, outcome, category FROM results"
NEW_READER = "SELECT company_id, coalesce(classifier_version, 'unknown') AS version FROM results"
stage 05 · tests/test_migrations.py
def test_old_reader_still_works_after_the_new_column_is_added():
    connection = database_at_version_2_with_one_row()
    migrate(connection)
    assert connection.execute(OLD_READER).fetchall() == [("c1", "suggested", "Food & Hospitality")]


def test_new_reader_handles_rows_written_before_the_column_existed():
    connection = database_at_version_2_with_one_row()
    migrate(connection)
    assert connection.execute(NEW_READER).fetchall() == [("c1", "unknown")]

What's happening: the tests build a database as it looked before step 3, with a real row in it, then upgrade it and run both readers.

Exercise 1 · Check (⏱️ ~3 min)

Q1: Why must a released migration never be edited?

Q2: Which change is safe while old code is still running?

Q3: What does migrate() do on a database that is already up to date?

Exercise 2 · Change: plan a rename the safe way (⏱️ ~20 min)

Goal: Rename a column without breaking anyone.

Instructions:

  1. The team wants evidence_excerpt renamed to evidence_sentence.
  2. Write the plan as three releases: expand (add the new column and fill it), switch (all code reads and writes the new one), contract (drop the old one).
  3. Implement only the expand step as a new migration, with an UPDATE that copies existing values.
  4. Write a test that an old reader using evidence_excerpt and a new reader using evidence_sentence both see the same data after the step.
Hint

SQLite's ALTER TABLE can add and drop columns; check the documentation for which version of SQLite you have before using DROP COLUMN in the contract step.

Exercise 3 · Transfer: how does your team change schemas? (⏱️ ~10 min)

For a database you work with, find where its schema changes are recorded. Check whether old code and new code ever run against it at the same time, and whether its recent changes were expand-only.
