📚 Core Concepts

Observe: the batch ran overnight. Did it work?

The Company Enricher now runs as a nightly batch. In the morning, the review team says the queue looks "really long today". Is something broken? With the Module 5 code there is no way to tell: no record of how many companies were processed, how many went to review, or why.

Start from the promises, not from the code. What do the people who depend on the service care about?

PromiseWhat would show it is broken
Most companies are categorised without a personthe share needing review jumps
Weak evidence goes to review, not to a wrong categoryprecision drops (Day 16 measures this offline)
A missing website does not stop the batchmany no_website reasons at once
Each company is processed in reasonable timeper-company duration grows

Say it plainly: events, counts, and one alarm

Stage 06 adds three things.

A structured event per company. After every enrichment the service logs one JSON line with named fields: the event name, a trace ID, the company ID, the outcome, the reason, and the category. Because it is JSON, a tool can answer "show every no_website from last night" without parsing sentences. The trace ID is a random identifier for that one enrichment, so every line about it can be found together.

Counters. Metrics counts outcomes and reasons and records each duration. From those, the review rate is one division.

One alert. review_rate_alert returns a message when more than 30% of results need review, the Day 16 target, but only after at least 20 results, so three unlucky companies at the start of a run do not wake anyone. The message includes the top reasons, so whoever reads it starts with a clue.

What not to log matters too. Log company IDs, outcomes, and reasons, not whole About pages or anything personal. OWASP's logging guidance warns against recording sensitive data in logs.

Name it: logs, metrics, traces

OpenTelemetry, a widely used open standard for this work, describes three main signals: logs are timestamped records of events, metrics are measurements aggregated over time, and traces follow one request through a system. This project keeps all three small and in-process: JSON log lines through Python's logging module, counters in a Metrics object, and a trace ID on each event. OpenTelemetry's own libraries are the next step when the service has more than one process.

Structured logging means writing events as fields rather than free text. An alert is a rule that tells a person when an indicator crosses a threshold.

None of the three books' freely available material covers logging, metrics, or alerting, so this lesson relies on official documentation only.

💻 Code Examples

Example 1: One event, one JSON line

stage 06 · enricher/observability.py
def log_event(logger, event, **fields):
    """Log one event as a single JSON line, so tools can search it by field."""
    logger.info(json.dumps({"event": event, **fields}, sort_keys=True))

Example 2: What the service records after each company

stage 06 · enricher/core/enrich.py
self.metrics.record(result, duration_ms=(time.perf_counter() - started) * 1000)
log_event(
    logger,
    "enrichment_finished",
    trace_id=trace_id,
    company_id=company.company_id,
    outcome=result.outcome.value,
    reason=result.reason.value if result.reason else None,
    category=result.suggestion.category.value if result.suggestion else None,
)

What's happening: every enrichment produces one counter update and one event, with exactly the fields the promise table needs.

Example 3: An alert that ignores noise

stage 06 · enricher/observability.py
def review_rate_alert(metrics, threshold=0.30, minimum_results=20):
    """Return an alert message when too many results need a person, else None.

    The minimum avoids alerting on a handful of unlucky results.
    """
    if metrics.total < minimum_results or metrics.review_rate <= threshold:
        return None
    return (
        f"review rate {metrics.review_rate:.0%} is above {threshold:.0%} "
        f"over {metrics.total} results; top reasons: {dict(metrics.reasons.most_common(3))}"
    )

Example 4: Testing what gets logged

stage 06 · tests/test_observability.py
def test_each_enrichment_logs_one_json_line(enricher, caplog):
    with caplog.at_level(logging.INFO, logger="enricher"):
        enricher.enrich(company("Lantern Lane Bakery"))

    event = json.loads(caplog.records[-1].getMessage())
    assert event["event"] == "enrichment_finished"
    assert event["outcome"] == "needs_review"
    assert event["reason"] == "weak_evidence"
    assert len(event["trace_id"]) == 32

Exercise 2 · Change: a second alert (⏱️ ~20 min)

Goal: Turn another promise into an alert.

Instructions:

  1. Promise: "a missing website does not stop the batch" holds, but many no_website results at once usually means the website source is broken.

  3. Write two tests: one where it fires, one where it stays quiet.
  4. Call it from __main__.py next to the review-rate alert.
Hint

metrics.reasons["no_website"] / metrics.total is the share. Reuse the shape of review_rate_alert.
