📚 Core Concepts

Observe: working code that could be clearer

Open exercises/day11_before_refactor.py in stage 03. It holds the version of enrich that existed before today's lesson. All 220 tests pass with it. But look at how it builds the result: it calls self._decide(suggestion) twice, once for the status and once inside the expression for the reason.

Nothing is broken. Yet a reader has to check that both calls give the same answer, and a future change to _decide (say, logging each decision) would now run twice. This is the kind of small, real untidiness that refactoring is for.

Say it plainly: the safe way to reshape code

A refactoring changes how the code is built without changing what it does. The only way to know "what it does" stayed the same is evidence, and the cheapest evidence is a test suite you trust.

The safe loop is:

  1. Pin the behaviour. Make sure tests cover what you might break. Stage 03 has test_same_decisions.py, which pins every sample company's decision, plus the promise tests from Day 9.
  2. Make one small change. Here: compute the status once, store it in a variable, and use it twice.
  3. Run the tests. All green means the step kept behaviour.
  4. Commit. A commit per step gives you a known-good point to return to.
  5. Repeat or undo. If a step turns the tests red and the fix is not obvious, do not debug forward; revert to the last commit and take a smaller step.

Mixing a refactoring with a behaviour change in the same step breaks the loop. If the tests fail, you cannot tell which change caused it.

Name it: refactoring, characterization tests, version control

The Pragmatic Programmer, Topic 40, "Refactoring", describes refactoring as a disciplined restructuring of existing code that does not change its external behaviour, done in small steps with good tests. The book's Topic 19, "Version Control" argues for keeping everything in version control, so any step can be undone.

John Ousterhout's A Philosophy of Software Design, Chapter 16, "Modifying Existing Code", adds the design view: when you change code, aim to leave the design better than you found it, as if it had been written that way from the start, rather than making the smallest possible patch.

Git provides the tools: git commit records a step; git revert creates a new commit that undoes an earlier one; git restore throws away uncommitted edits.

The Pragmatic Programmer's Topic 27, "Don't Outrun Your Headlights", available as the publisher's free excerpt on the book page, explains why the steps stay small: take a step, get feedback, then decide the next one, instead of committing to a long plan you cannot see the end of. Its tips in the publisher's official list of the book's tips include Tip 42 (p. 126), "Take Small Steps - Always", Tip 65 (p. 212), "Refactor Early, Refactor Often", and Tip 28 (p. 85), "Always Use Version Control".

💡
Key Insight: Tests make refactoring safe, small steps make failures easy to locate, and commits make every step reversible.

🔑 Key Terminology

Refactoring
Restructuring existing code without changing its external behaviour.
Paraphrased from Thomas and Hunt, The Pragmatic Programmer, 20th Anniversary Edition, Topic 40, "Refactoring"
Characterization test
A test that pins what the code does today, so a change that alters it fails.
Standard software vocabulary; this plain definition is course-authored
Commit
A saved snapshot of changes in Git, with a message explaining them.
Official Git vocabulary (git-commit)
Revert
A new commit that undoes the changes of an earlier commit.
Official Git vocabulary (git-revert)
Version control
A system that records every change to files so any earlier state can be recovered.
Paraphrased from Thomas and Hunt, The Pragmatic Programmer, 20th Anniversary Edition, Topic 19, "Version Control"

status = self._decide(suggestion)
result = EnrichmentResult(
    company_name=company_name,
    status=status,
    reason=None if status == ACCEPTED else WEAK_EVIDENCE,
    suggestion=suggestion,
    evidence_url=page.url,
    evidence_text=page.main_activity,
    checked_at=self._clock(),

What's happening: same fields, same values, same decisions. The tests cannot tell the two versions apart, which is exactly the point.

Example 3: The evidence that made it safe

stage 03 · tests/test_same_decisions.py
@pytest.mark.parametrize("company, category", DECISIONS.items())
def test_decision_is_unchanged(enricher, company, category):
    result = enricher.enrich(company)
    assert (result.suggestion.category if result.status == ACCEPTED else None) == category

What's happening: twelve companies, including the missing website, each checked before and after every step.

Example 4: The loop in Git

bash
python -m pytest -q                      # green before you start
git commit -am "Compute the enrichment status once"
python -m pytest -q                      # red? undo the last commit:
git revert --no-edit HEAD

What's happening: each step is a commit, so undoing one is a command, not an archaeology project.

Exercise 1 · Check (⏱️ ~3 min)

Q1: Which change is a refactoring?

Q2: The tests turn red after a refactoring step and the cause is not obvious. What next?

Q3: Why not refactor and change behaviour in the same commit?

Exercise 2 · Change: a refactoring sequence (⏱️ ~20 min)

Goal: Practise the loop on real code.

Instructions:

  1. Work in a copy of stages/03-change-safely inside a Git repository.
  2. Step 1: extract a method _result_from(company_name, page, suggestion) that builds the EnrichmentResult. Run the tests, then commit.
  3. Step 2: move the check_confidence call inside _result_from. Run the tests, then commit.
  4. Step 3: deliberately break something (change >= to > in _decide). Run the tests, watch which fail, then git restore the file.
  5. Use git log --oneline to see your steps.
Hint

Step 3 should fail no characterization test, because no sample company scores exactly 0.82. Ask yourself what test would catch it, and add it.

Exercise 3 · Transfer: pin before you change (⏱️ ~10 min)

Pick a function you have wanted to clean up. Before touching it, write down which tests would tell you that its behaviour changed. If none exist, write one characterization test first.
