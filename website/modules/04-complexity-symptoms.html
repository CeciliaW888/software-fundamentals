Recognise complexity by its symptoms

📚 Core Concepts

Observe: one small change request

The business asks for one new category: Agriculture, for farms and growers. That sounds like a one-line job. Try it on the Module 1 code in stages/01-read-code/enricher.py and count what you touch.

  1. Add "Agriculture" to the CATEGORIES list.
  2. Add an "Agriculture" entry to CATEGORY_KEYWORDS.
  3. Put it in the right position, because predict_proba returns probabilities in CATEGORIES order and suggest turns a position back into a name.
  4. Check the line if confidence == 1 / len(CATEGORIES):, which decides when the answer is "Other". It silently depends on how many categories exist.

Four places, and two of them need knowledge that the code does not state anywhere. Now a second request: raise the confidence threshold from 0.82 to 0.85. The number appears as the default in select_confident_category_suggestions and again inside suggest_company_category. Miss one and the two functions disagree.

Say it plainly: three ways code makes changes hard

Each problem you just hit has a different shape.

  • One change, many edits. The threshold lives in two places, so one decision needs two edits.
  • Too much to hold in your head. To add a category you must remember that a list's order and a dictionary's keys must agree.
  • Things you didn't know you needed to know. Nothing near CATEGORY_KEYWORDS warns you about the 1 / len(CATEGORIES) check.

The last one is the worst. The first two slow you down; the third lets you ship a bug with confidence.

Name it: the three symptoms

John Ousterhout's A Philosophy of Software Design, Chapter 2, "The Nature of Complexity" (to verify against book), names these symptoms. Change amplification is when a simple change needs edits in many places. Cognitive load is how much a developer must know to complete a task. Unknown unknowns are cases where it is not obvious which code must change, or what you need to know to change it.

He describes the causes as dependencies (code that cannot be understood or changed on its own) and obscurity (facts a reader needs but cannot see in the code). The duplicated threshold is a dependency; the hidden 1 / len(CATEGORIES) rule is obscurity.

The Pragmatic Programmer adds a warning about time in its Topic 3, "Software Entropy" (to verify against book): small signs of neglect left unfixed invite more of the same, which the authors call "broken windows". A second duplicated constant is easier to add once the first one is tolerated.

The fix in Module 2 is to put each piece of knowledge in exactly one place. In stages/02-control-complexity, all category knowledge lives in categories.py, and the threshold is defined once.

The three symptoms are not only in Chapter 2 (to verify against book): Ousterhout lists them again in his chapter on why to write comments, which is included in Ousterhout's free 2nd-edition extract. The Pragmatic Programmer's Topic 8, "The Essence of Good Design" (to verify against book), offers one yardstick for every design choice. Its Tip 14 (p. 28 in the publisher's official list of the book's tips) is "Good Design Is Easier to Change Than Bad Design", which is exactly what today's scoring measures.

💡
Key Insight: Count the edits and the facts a change needs. That count is a measure of complexity you can compare before and after.

🔑 Key Terminology

Complexity
Anything about the structure of a system that makes it hard to understand and modify.

Change amplification
A simple change requiring edits in many different places.
Paraphrased from John Ousterhout, A Philosophy of Software Design, 2nd ed., Chapter 2 (to verify against book)
Cognitive load

Paraphrased from John Ousterhout, A Philosophy of Software Design, 2nd ed., Chapter 2 (to verify against book)

💻 Code Examples

Example 1: Before, category knowledge in several places

stage 01 · enricher.py
class KeywordCategoryClassifier:
    def suggest(self, activity_summary):
        """Return the most likely category and its confidence."""
        probabilities = self.predict_proba([activity_summary])[0]
        confidence = max(probabilities)
        if confidence == 1 / len(CATEGORIES):
            return CategorySuggestion("Other", confidence)
        return CategorySuggestion(CATEGORIES[probabilities.index(confidence)], confidence)

What's happening: to read this you must know that probabilities come back in CATEGORIES order, that "Other" has no keywords, and that equal probabilities mean "no keywords found". None of that is written down here.

Example 2: After, one place for category knowledge

stage 02 · enricher/categories.py
OTHER = "Other"

CATEGORIES = [*CATEGORY_KEYWORDS, OTHER]

MINIMUM_CONFIDENCE = 0.82

What's happening: the category list is built from the keyword dictionary, so they cannot disagree. The threshold has one definition that every other module imports.

Example 3: A test that scores the change

stage 02 · tests/test_enricher.py
def test_adding_a_category_is_one_edit(monkeypatch):
    from enricher import categories

    monkeypatch.setitem(categories.CATEGORY_KEYWORDS, "Agriculture", {"farm", "crops"})
    suggestion = KeywordCategoryClassifier().suggest("We farm crops")
    assert suggestion.category == "Agriculture"

What's happening: the test adds a category with one dictionary entry and checks that the classifier can suggest it. If someone reintroduces a second place to edit, this test fails.

Exercise 2 · Change: score the change before and after (⏱️ ~15 min)

Goal: Measure complexity instead of arguing about it.

Instructions:

  1. Make a two-column table: "Module 1 code" and "Module 2 code".
  2. For the request "add Agriculture", count the files and lines you must edit in each version.
  3. Count the facts you must know that are not written next to the code you edit.
  4. Do the same for "change the threshold to 0.85".
  5. Run the stage 02 tests to confirm the after-version works: cd stages/02-control-complexity && python -m pytest -q.
Hint

In stage 02, categories.py is the only file to edit for both requests. Search the stage for 0.82 to confirm it appears once.

Exercise 3 · Transfer: find a broken window (⏱️ ~10 min)

Open any codebase you know. Find one duplicated constant, one magic number, or one rule that lives in two places. Write down the change request that would expose it and how many edits it would need.
