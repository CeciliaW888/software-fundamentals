📚 Core Concepts

Observe: two reviewers, one bakery

Lantern Lane Bakery is in the review queue. Two reviewers open it at almost the same moment. Reviewer A decides Food & Hospitality; reviewer B decides Manufacturing.

The obvious code for "confirm a category" is: check whether a confirmation already exists; if not, insert one. The exercise file day20_check_then_insert.py does exactly that. The test test_two_reviewers_can_both_confirm_without_a_constraint runs the steps in this order, with two separate database connections:

  1. A checks: no confirmation yet.
  2. B checks: no confirmation yet.
  3. A inserts Food & Hospitality.
  4. B inserts Manufacturing.

Both inserts succeed. The bakery now has two confirmed categories, and every report that assumes one will be wrong. Nothing crashed; the data is simply inconsistent.

Say it plainly: the check and the act must be one step

The rule is: a company has at most one confirmed category. A rule that must always be true is an invariant.

Each reviewer's check was correct when it ran. The problem is the gap between the check and the insert, during which the other reviewer acted. Any rule enforced by "look first, then write" has that gap, however fast the code is.

The fix is to let the place where both writes meet, the database, refuse the second one. Migration 4 adds a unique index on confirmations (company_id). Now step 4 fails with an IntegrityError, whatever order the steps run in. SqliteResultStore.confirm_category turns that error into a domain exception, AlreadyConfirmed, so the reviewer screen can say "someone else confirmed this first" instead of showing a database error.

Name it: invariants, aggregates, isolation

An invariant is a rule that must always hold. A race condition is a bug where the result depends on the timing of concurrent actions; check-then-act is the classic shape.

Eric Evans's Domain-Driven Design, Chapter 6, "The Life Cycle of a Domain Object" (to verify against book), introduces the aggregate: a cluster of objects treated as one unit for data changes, with a boundary inside which invariants must always be consistent. Here, a company together with its confirmation is that unit, and the database constraint is how the boundary is enforced.

The Pragmatic Programmer, Topic 34, "Shared State Is Incorrect State", warns that whenever two processes share a resource, you must make access to it atomic, or race conditions follow.

Databases describe how concurrent transactions see each other as isolation. SQLite's documentation explains its isolation behaviour, including that only one connection can write at a time; PostgreSQL's documentation describes its isolation levels and the anomalies each allows. Neither makes a check-then-act sequence safe on its own: in this example each check runs before either write, so a constraint is the dependable guard.

The Pragmatic Programmer's Topic 34, "Shared State Is Incorrect State", available as the publisher's free excerpt on the book page, tells the same story with a diner, two waiters, and the last slice of pie: each waiter checks the display case and promises the slice, because the check and the taking are not one indivisible step. The book's remedies are mutual exclusion and, better, making the shared resource itself responsible for its own consistency, so callers cannot forget to protect it. The unique index is that second remedy: the database, not each reviewer's code, guards the rule. Evans's free DDD Reference explains why the rule needs one owner: an aggregate draws a boundary around objects whose consistency rules must hold together, and changes inside it are applied as one unit.

💡
Key Insight: Enforce an invariant at the single point every writer must pass through. For stored data, that is usually a database constraint.

🔑 Key Terminology

Invariant
A rule that must always be true, such as "a company has at most one confirmed category".
Standard software vocabulary; this plain definition is course-authored
Race condition
A bug where the outcome depends on the timing of actions that happen at the same time.
Standard software vocabulary; this plain definition is course-authored
Aggregate
A cluster of objects treated as one unit for changes, with a boundary inside which invariants must hold.
Paraphrased from Eric Evans, Domain-Driven Design, Chapter 6 (to verify against book)
Unique index
An index that refuses two rows with the same value in its columns.
Official SQLite vocabulary (CREATE INDEX)
Transaction
A group of database changes that succeed or fail together.
Official SQLite vocabulary (transactions)
Isolation
How much one transaction can see of another's changes while both are running.
Official SQLite vocabulary (isolation in SQLite)

💻 Code Examples

Example 1: The unsafe pattern

stage 05 · exercises/day20_check_then_insert.py
def no_confirmation_yet(connection, company_id):
    row = connection.execute(
        "SELECT 1 FROM confirmations WHERE company_id = ?", (company_id,)
    ).fetchone()
    return row is None

What's happening: the answer is true when it is read, and may be false a moment later.

Example 2: Reproducing the race

stage 05 · tests/test_confirmation_race.py
def test_two_reviewers_can_both_confirm_without_a_constraint(tmp_path):
    reviewer_a, reviewer_b = shared_database(tmp_path, with_unique_index=False)

    a_sees_none = no_confirmation_yet(reviewer_a, "c1")
    b_sees_none = no_confirmation_yet(reviewer_b, "c1")
    insert_confirmation(reviewer_a, "c1", "Food & Hospitality", "a", "t1")
    insert_confirmation(reviewer_b, "c1", "Manufacturing", "b", "t2")

    assert a_sees_none and b_sees_none
    assert reviewer_a.execute("SELECT count(*) FROM confirmations").fetchone()[0] == 2  # the invariant is broken

What's happening: the test runs the steps in the bad order on purpose, so the race happens every time instead of once a month in production.

Example 4: A database error becomes a domain answer

stage 05 · enricher/adapters/sqlite_store.py
def confirm_category(self, company_id, category: Category, reviewer, at: datetime):
    """Record a reviewer's confirmed category. Only the first one wins."""
    try:
        with self.connection:
            self.connection.execute(
                "INSERT INTO confirmations (company_id, category, confirmed_by, confirmed_at)"
                " VALUES (?, ?, ?, ?)",
                (company_id, category.value, reviewer, at.isoformat()),
            )
    except sqlite3.IntegrityError as error:
        raise AlreadyConfirmed(company_id) from error

What's happening: no check before the insert at all; the insert either wins or is refused, in one step.

Exercise 2 · Change: a reviewer changes their mind (⏱️ ~20 min)

Goal: Change an invariant-protected value safely.

Instructions:

  1. Reviewers may correct a confirmation, but only the reviewer who made it.
  2. Add change_confirmation(company_id, category, reviewer, at) to SqliteResultStore using one UPDATE ... WHERE company_id = ? AND confirmed_by = ?.
  3. Check the number of changed rows (cursor.rowcount) and raise a domain error when it is zero.
  4. Write two tests: the original reviewer can change it; another reviewer cannot.
Hint

Putting the reviewer condition inside the WHERE makes the check and the change one statement, so there is no gap.

Exercise 3 · Transfer: find a check-then-act (⏱️ ~10 min)

Search a codebase you know for a pattern like "if not exists, then create" or "if balance enough, then subtract". Decide whether two users could hit it at once, and what would enforce the rule in one step.

def review_queue(self, limit=20):
    """Access pattern 3: results waiting for a person, oldest first."""
    return self.connection.execute(
        "SELECT * FROM results WHERE outcome = ? ORDER BY checked_at LIMIT ?",
