Read contracts before bodies

Decide what callers may rely on before implementation details tempt you to rely on the wrong things.

Tangible winYou will extract a callable contract and prove it with a test that survives an implementation change.
Mission link: safe change begins by separating a module’s promises from the machinery currently used to keep them.

Every callable has two surfaces

The interface is everything another part of the system must know to use a callable correctly. The implementation is how the callable keeps those promises today.

A signature exposes part of the interface, but types cannot express every return condition, side effect, failure, or precondition. Those remaining promises still belong to the contract.

01 · FORMAL

Read the declaration

Name, parameters, types, return type, and declared exceptions constrain valid calls.

02 · INFORMAL

Find the promises

Behaviour, edge cases, side effects, failures, and preconditions complete the contract.

03 · HIDDEN

Ignore the machinery

Helpers, retries, batching, SQL, and algorithms may change without changing callers.

Body-first reading creates accidental dependencies

Suppose you find this service function with no useful interface documentation:

Implementation visible, contract missing
def classify_document(
    document: Document,
    classifier: Classifier,
    store: ResultStore,
) -> Classification | None:
    chunks = split_into_token_batches(
        document.text,
        max_tokens=512,
    )
    probabilities = retry_twice(
        lambda: classifier.predict(chunks)
    )
    result = choose_top_class(probabilities)

    if result.confidence < 0.82:
        return None

    store.save(document.id, result)
    return result

You can infer several facts by tracing this body, but not every fact deserves to become a promise. The 512-token batches and retry helper are replaceable machinery. The return condition and persistence side effect affect callers, so they belong in the interface.

Retrieval check

Which fact belongs in the interface contract?

A contract should hide more than it reveals

Now the callable can be understood without opening its body:

Caller-facing declaration
def classify_document(
    document: Document,
    classifier: Classifier,
    store: ResultStore,
) -> Classification | None:
    """Classify a document and persist accepted results.

    Return the highest-confidence classification when its
    confidence is at least 0.82. Return None below that
    threshold without writing to the store.

    Persist an accepted result before
    returning it. Raise ClassificationUnavailable
    if classification cannot produce a result.
    """
    ...

The contract states behaviour, return semantics, side effects, and failure. It deliberately omits tokenisation, retry count, and storage technology. That omission creates room to change the implementation safely.

Your turn: separate promise from machinery

Select every fact a caller must know. Leave replaceable implementation details unselected.

Three promises and two implementation details are mixed together.

Test the promise, not the machinery

A contract test should keep passing if batching, retries, or storage technology changes:

Observable contract test
def test_rejected_result_is_not_saved():
    classifier = classifier_returning(confidence=0.61)
    store = recording_store()

    result = classify_document(
        sample_document(),
        classifier,
        store,
    )

    assert result is None
    assert store.saved_results == []

This test knows the return and side-effect promises. It does not know how many chunks, retries, helper calls, or SQL statements occur.

A contract is the smallest complete set of facts another module must know. Missing facts create surprises; implementation facts create coupling.

Apply it to real code

Choose one function you did not write. Before opening its body, write down its expected result, side effects, failures, and preconditions. Then inspect the implementation only to test whether those promises are accurate and complete.
