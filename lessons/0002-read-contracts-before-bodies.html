Know what a function promises

Before reading every line, find what goes in, what may come back, what else changes, and what can fail.

Your resultYou will describe one function clearly and test what other code is allowed to rely on.
Plain idea: other code should depend on a function’s promised result, not on the temporary steps inside it.

Start with a real question

Our service receives a customer name, finds the official website, reads its About page, summarises the business activity, and suggests a code from the Australian and New Zealand Standard Industrial Classification (ANZSIC).

If another part of the service uses that suggestion, what does it need to know?

01 · IN

What goes in?

A customer name, an industry classifier, and a place to save results.

02 · OUT

What may come back?

An industry suggestion, or None when the evidence is not strong enough.

03 · ELSE

What else happens?

An accepted suggestion is saved; website or classification work may fail.

Read the work once

This function shows the whole flow:

How the work happens today
def suggest_customer_industry(
    customer_name,
    classifier,
    store,
):
    website = find_official_website(
        customer_name
    )
    about_text = read_about_page(website)
    activity_summary = (
        summarise_business_activity(
            about_text
        )
    )
    suggestion = classifier.suggest(
        activity_summary
    )

    if suggestion.confidence < 0.82:
        return None

    store.save(customer_name, suggestion)
    return suggestion

Some facts affect other code. A weak suggestion returns None. A returned suggestion has already been saved.

Other facts are only today’s method: which service finds the website, which tool reads the page, which model suggests the code, how often the service tries again, and where it saves the result.

Quick check

Which fact must code using this function be able to rely on?

Write down the promise

Python lets us place an explanation directly under the function name. This is called a docstring.

Understand the function without opening its body
def suggest_customer_industry(
    customer_name,
    classifier,
    store,
):
    """Suggest an ANZSIC industry.

    Find the official website.
    Read its About page.
    Use classifier to propose a code.
    Use store to save an accepted result.
    Return the saved result when its
    confidence is at least 0.82.
    Return None when evidence is weaker.

    Raise WebsiteUnavailable when no
    suitable page can be read.
    """
    ...

This explanation states the result, the low-confidence case, the saved change, and one failure. WebsiteUnavailable is a course-authored name for the error raised when no suitable page can be read.

It leaves out replaceable details: which service finds the website, which tool reads the page, which model suggests the code, how often it tries again, and where it saves the result.

Test the promise

A useful test checks what other code can observe. It does not check which helper or library was used.

A test that can survive an internal rewrite
def test_weak_suggestion_is_not_saved():
    classifier = classifier_returning(
        anzsic_code="3011",
        confidence=0.61,
    )
    store = recording_store()

    result = suggest_customer_industry(
        "Example Customer",
        classifier,
        store,
    )

    assert result is None
    assert store.saved_suggestions == []

The test checks two visible results: the function returns None, and the store remains unchanged.

Where the technical words come from

WordPlain meaningWhere it comes from
FunctionA named block of code that performs a job.Official Python vocabulary
DocstringText inside a function that explains how to use it.Official Python vocabulary
NonePython’s built-in marker for “no value here.”Official Python vocabulary
InterfaceWhat other code must know to use a function or module.Standard software vocabulary; central in Ousterhout Chapter 4
ImplementationThe steps currently used to do the work.Standard software vocabulary; central in Ousterhout Chapter 4
Two words you do not need yet

Contract appears in broader software-engineering writing as shorthand for promised behaviour. The reviewed Ousterhout chapters do not use it, and this course does not require it.

Callable is official Python vocabulary for anything that can be used with function-call syntax. This lesson uses the narrower word function.
