Names are architecture in miniature

Refactor one opaque classification function until its data, decision, and confidence rule are visible without a comment.

Tangible winYou will turn a plausible generated or inherited function into code another engineer can review safely.
Mission link: reliable systems begin with code whose behaviour can be understood before it is changed, tested, or deployed.

The risk is hidden context

Classification code can look simple while carrying several invisible meanings: which component produced a score, what the score measures, which processing stage the data belongs to, and which threshold changes a business decision.

A short name saves keystrokes once. An intention-revealing name saves reconstruction every time the code is reviewed, debugged, or changed.

01 · OBJECT

Name the thing

Prefer the domain object over containers such as data, items, or x.

02 · STAGE

Name the state

Distinguish raw, validated, embedded, retrieved, ranked, and generated forms.

03 · DECISION

Name the choice

Functions should reveal the transformation or decision, not merely say run or process.

Read the two versions

These functions behave the same. The second version carries the context the first version forces you to reconstruct.

Opaque
def run(xs, m, t=0.82):
    r = m.predict_proba(xs)
    return [
        x for x, p in zip(xs, r)
        if max(p) >= t
    ]
Intent visible
def select_high_confidence_documents(
    documents,
    classifier,
    minimum_confidence=0.82,
):
    probabilities_by_document = (
        classifier.predict_proba(
            documents
        )
    )
    return [
        document
        for document, class_probabilities
        in zip(
            documents,
            probabilities_by_document,
        )
        if max(class_probabilities)
        >= minimum_confidence
    ]

The algorithm did not become more sophisticated. The design became more explicit: documents enter, a classifier produces class probabilities, and a confidence rule selects a subset.

Retrieval check

Without looking back, what is the strongest reason to rename t to minimum_confidence?

Your turn: refactor without changing behaviour

Rename only. Do not add comments or change the algorithm. Make the domain object, model role, score meaning, and selection decision explicit.

Five design signals are waiting to be made explicit.

  • The function says it selects or filters a result.
  • The inputs name documents or records, not xs.
  • The model role is explicit, not m.
  • The threshold names confidence and its meaning.
  • Predictions or probabilities replace r and p.
Naming is not decoration. It is the first layer of the system contract, written for the next reader.

Apply it to real service code

In your next code review, find one name that hides a stage, unit, or decision. Rename it before adding a comment. If the rename is difficult, the underlying responsibility may still be unclear.

Primary reading and sources

Primary design reading: John Ousterhout, A Philosophy of Software Design, Chapter 14, “Choosing Names,” especially precise and consistent names.
Counterpoint: Robert C. Martin, Clean Code, Chapter 2, “Meaningful Names.” Compare both authors by asking which name reduces obscurity without adding noise.
PEP 8: Function and Variable Names specifies Python’s lowercase, underscore-separated convention. Convention supports readability, but it does not replace domain meaning.
Pearson: Clean Code describes the book’s principles, practices, and case-study structure.
